## 二、行业标准功能点清单（整理后）

### A. 医保结算经办系统（按业务域拆分）

**A1 参保管理域**
- 单位参保登记 / 职工参保登记 / 城乡居民参保登记
- 参保信息变更（个人/单位）
- 参保暂停、恢复、终止（停保、退保）
- 医保关系转移接续（跨统筹区）
- 缴费年限核定 / 参保信息查询

**A2 定点协议管理域**
- 定点医药机构申请与准入评估
- 协议签订 / 协议变更 / 协议续签
- 年度考核评价、协议解除与退出
- 定点机构基础信息库（编码、资格、状态）

**A3 就医结算域（核心经办链路）**
- 医院侧报盘（结算清单上传，编码规范校验）
- 联网即时结算（待遇计算：起付线/比例/乙类先行自付/个账划扣）
- 日对账（平台与机构双方账核对）
- 日拨付 / 按笔拨付（T+1 汇总、电子回单回传、次月扣减）——即时结算改革核心
- 月度申报（每月 10 日前，已完成对账的费用）
- 智能审核（初审→申诉→复审→合议→扣款）
- 月度结算（月拨付比例 − 审核扣款 − 已拨付日拨付 − 其他扣减）
- 月度基金拨付（生成支付计划、财务拨付、凭证）
- 预留质量保证金
- 年终清算（年度支出核定、权重/费率测算、特例单议、考核、清账）
- 结算单管理（明细、退费冲正）

**A4 费用报销域（参保人侧零星报销）**
- 门诊费用手工报销
- 住院费用手工报销
- 药店购药费用报销
- 报销受理 → 审核 → 拨付 → 办结

**A5 个人账户域**
- 个人账户划入 / 查询
- 个人账户一次性支取（清退，死亡/退保）
- 个人账户转移

**A6 待遇认定域**
- 门诊慢特病病种待遇认定
- 生育保险待遇核准支付
- 医疗救助对象手工报销

**A7 异地就医域**
- 异地就医备案（长期居住/转诊转院/临时外出）
- 备案变更 / 撤销
- 异地就医直接结算

**A8 报表与决算域**
- 基金运行分析、拨付分析、险种维度统计
- 经办效率 / 审核扣款统计

### B. 医保基金监管系统（按能力拆分）

**B1 两库建设** —— 规则库 + 知识库（临床指南/医学/药品知识库）
**B2 三道防线**
- 事前提醒（机构端嵌入：开方/医嘱/结算前实时比对规则，防冒名、预警超量开药）
- 事中审核（结算关口实时校验，明确违规拒付 / 可疑转人工）
- 事后监管（全量历史数据挖掘、关联分析、趋势比对、线索锁定）
**B3 智能审核与监控** —— 线上初审/复核/申诉/复审/反馈闭环，规则参数可配
**B4 监督检查** —— 飞行检查、专项检查、日常巡查、双随机一公开、专家审查
**B5 举报投诉与奖励** —— 举报受理、核查处置、反馈、举报奖励、隐私保护
**B6 信用管理** —— 信用评价、积分/"驾照式"记分、守信激励 / 失信联合惩戒名单
**B7 大数据反欺诈** —— 几十种大数据模型、线索发现、调查取证、违规处理、结果应用闭环
**B8 支付改革监管** —— DRG/DIP 支付方式下智能审核与监管
**B9 场景与追溯** —— 药品追溯码监管、药品耗材进销存实时管理、视频监控/生物特征识别（防挂床/冒名）
**B10 行刑衔接与行政端** —— 行政检查执法全流程指挥调度、行刑衔接、案件移送
**B11 社会监督** —— 信息披露、社会监督员、典型案例曝光、自查自纠

## 三、CSMIS 已实现功能（源码核实）

| 模块（前端路由） | 后端实现 | 说明 |
|------|------|------|
| 经办工作台 | `WorkbenchController` | 今日 KPI、待办、近 10 日趋势 |
| 门诊/住院医保结算 | `SettleController` + `SettleEngine` | 待结算→试算→确认；待遇计算（起付/比例/乙类自付/个账） |
| 结算单管理 | `BillController` | 明细、退费冲正 |
| 机构报盘接收 | `GatewayController` + `SettlementGatewayServiceImpl` | 2304 上传 / 2305 撤销 / 日对账；2304 平台侧即时核定 |
| 月度结算管理 | `MonthlyController` + `MonthlyServiceImpl` | 申报→审核→拨付→年终清算 状态机（1→2→3→4）；质保金预留/返还 |
| 参保人管理 | `InsuredPersonController` | 分页查询、新增/同步（按身份证幂等）——**仅查询+同步** |
| 费用审核 | `FeeAuditController` + `FeeAuditServiceImpl` | 待审核分页、通过 / 驳回——**无申诉/复审/合议** |
| 三大目录与对照 | `CatalogController` + `MappingController` | 目录分页统计、院内项目人工/自动对照 |
| 异地就医备案 | `FilingController` | 备案增改与撤销 |
| 清算对账 | `ReconController` | 月度账期对账平账（日对账在 Gateway 内） |
| 统计报表 | `StatsController`（前端 `stats`） | ECharts 图表 |
| 监管工作台 | `SuperviseDashboardController` | 监管概览 |
| 规则配置 | `SuperviseRuleController` + `SuperviseRuleEngine` | 审核规则增改、启停——**仅规则库，无知识库** |
| 疑点稽核 | `SuperviseSuspicionController` | 跑规则→确认/排除（确定性规则，末位命中） |
| 飞检任务 | `SuperviseInspectionController` | 启动/完成/转追回；类型含专项检查/日常巡查/举报核查 |
| 违规追回 | `SuperviseRecoverController` | 追回 / 核销 |
| 系统管理 | 7 个 `System*` Controller | 用户/角色(菜单授权)/菜单/岗位/字典/科室/员工(资质) —— RBAC 完整 |

**已具备的亮点链路**：报盘→即时结算→对账→月度申报→智能审核扣款→质保金→月度拨付→年终清算（经办）+ 规则配置→疑点稽核→飞检→违规追回（监管），两条链路闭环，且三大目录对照、异地备案、完整 RBAC 都在。

## 四、差距分析矩阵（核心）

> 差距等级：**缺失（重要）** = 行业标配且无；**缺失（中/低）** = 非核心或渠道/行政层；**薄弱** = 有但功能浅/简化；**已覆盖** = 具备对应能力。

### 4.1 医保结算经办侧

| 功能点 | 行业标准要求 | CSMIS 现状 | 差距 | 建议 |
|------|------|------|------|------|
| 参保登记 / 信息变更 | 单位+个人登记、变更、暂停/恢复/终止 | 仅参保人查询+按身份证新增同步 | **缺失（重要）** | 增参保登记、变更、停保/退保流程 |
| 医保关系转移接续 | 跨统筹区转移、缴费年限核定 | 无 | **缺失（中）** | 补转移接续与年限核定 |
| 定点协议管理 | 申请准入、协议签订/变更/续签、年度考核、退出、机构信息库 | 完全无 | **缺失（重要）** | 建定点机构信息库 + 协议管理模块 |
| 手工（零星）报销 | 门诊/住院/药店费用报销，受理→审核→拨付→办结 | 无 | **缺失（重要）** | 补参保人侧报销经办（高频事项） |
| 门诊慢特病待遇认定 | 病种备案与待遇核准 | 无 | **缺失（中）** | 补待遇认定模块 |
| 个人账户管理 | 划入/查询/一次性支取(清退)/转移 | 仅结算时个账划扣，无独立账户管理 | **缺失（中）** | 补个人账户管理（清退/划转） |
| 生育保险 / 医疗救助报销 | 生育待遇、救助对象手工报销 | 无 | **缺失（低）** | 按演示范围取舍 |
| **日拨付 / 按笔拨付** | T+1 按笔拨付、电子回单回传、次月扣减（即时结算改革核心） | 仅有月度拨付+质保金返还，无日拨付 | **缺失（重要）** | 补日拨付批次+回单+次月扣减，体现"即时结算" |
| 结算清单质控 | 编码规范校验、清单上传与质控 | 有 2304 报盘，但无清单级编码/质控校验 | **已补齐** ✅ | 增结算清单校验与质控看板（见 7.3 第 17 项） |
| 智能审核申诉/复审/合议 | 初审→申诉→复审→合议闭环 | 费用审核仅通过/驳回 | **薄弱（重要）** | 补申诉→复审→合议流程与时限 |
| 多渠道经办（网办/掌办/短信） | 网办、掌办、高拍仪、短信反馈 | 无（单端后台） | **缺失（低）** | 演示平台可不做 |
| 统计报表深度 | 基金运行/拨付/险种多维分析 | ECharts 图表存在，深度待确认 | **已补齐** ✅ | 视需求补基金运行分析报表（见 7.3 第 19 项） |

### 4.2 医保基金监管侧（缺口更集中）

> **复核更正（开发阶段核实）**：初版调研按 Controller/表清单判断「事前提醒、事中拦截、大数据反欺诈、举报投诉」为完全缺失，
> 实际开发时逐个打开源码复核后发现：**这四项的表结构、菜单、前端页面、接口契约均已存在**，
> 但 `PrecheckServiceImpl.evaluate()` 与 `FraudServiceImpl.run()` 只做「随机取机构/人员 → 拼一个假单号 → 落一条假命中」，
> 即**只有骨架、没有真实判定**，且两者均未接入结算链路。下表中的「缺失」应理解为「真实能力缺失」，本轮已按真实引擎重做。

| 功能点 | 行业标准要求 | CSMIS 现状 | 差距 | 建议 |
|------|------|------|------|------|
| 两库—知识库 | 临床指南/医学/药品知识库 | 仅规则库（`SuperviseRule`） | **缺失（重要）** | 建知识库（临床规则/药品知识） |
| **事前提醒** | 机构端嵌入，开方/医嘱/结算前实时比对（第一道防线） | 页面/表存在，但 `evaluate()` 为伪造数据，未接入结算 | **缺失（重要）** | 增机构端事前提醒/拦截能力 |
| 事中实时审核 | 结算关口明确违规拒付/可疑转人工 | 结算时即时核定待遇，监管维度事中拦截未独立 | **薄弱** | 把监管规则嵌入结算事中环节 |
| 事后大数据反欺诈 | 几十种模型、关联/趋势分析、线索库 | `FraudServiceImpl.run()` 为伪造线索，无真实模型 | **薄弱（重要）** | 建大数据分析模型库 + 线索管理 |
| 举报投诉 + 奖励 | 举报受理/核查/反馈/奖励/隐私保护 | 后端状态机真实存在，**前端页面与菜单缺失** | **薄弱（中）** | 补举报投诉前端 + 奖励发放 |
| 信用管理 | 信用评价、积分/驾照式记分、守信激励/失信惩戒 | 无 | **缺失（重要）** | 建信用评价与记分、联合奖惩名单 |
| 双随机一公开 | 随机抽取、公开、专项整治行动管理 | 飞检含日常/专项类型，但无随机抽取与公开 | **薄弱（中）** | 补双随机抽取 + 结果公开 |
| 自查自纠 | 机构自查上报、整改闭环 | 无 | **缺失（中）** | 补自查自纠任务与整改跟踪 |
| **DRG/DIP 监管** | 支付方式下智能审核与监管 | 无 | **缺失（重要）** | 补 DRG/DIP 支付监管场景 |
| 药品追溯码监管 | 追溯码核验防串换 | 无 | **已补齐** ✅ | 补追溯码核验（见 7.3 第 18 项） |
| 进销存实时管理 | 药品耗材进销存 | 无 | **已补齐** ✅ | 补进销存（见 7.3 第 20 项） |
| 场景监控 | 视频监控、生物特征防挂床/冒名 | 无 | **缺失（中）** | 演示可放后续 |
| 行刑衔接/行政端 | 执法指挥调度、案件移送 | 无（仅经办端） | **缺失（低，边界外）** | 属行政端，可选 |
| 信息披露/社会监督 | 曝光、社会监督员、自查自纠 | 无 | **缺失（低/中）** | 演示可放后续 |

## 五、差距总览与优先级建议

### 已具备（不必补）
经办核心链路（报盘→结算→对账→申报→审核→拨付→清算）、三大目录对照、异地备案、费用审核（基础）、疑点稽核、飞检、违规追回、完整 RBAC 系统管理。

### 优先补（高价值、行业强标、缺口大）
1. **基金监管"三道防线"补齐**：事前提醒 + 事中实时审核拦截 + 事后大数据反欺诈模型（当前只有事后确定性规则）。
2. **两库之知识库**：从"只有规则库"升级为规则库+知识库（临床/医学/药品）。
3. **结算经办参保与协议管理**：参保登记/变更/停保、定点协议管理、手工（零星）报销——这是经办政务服务事项清单里的高频事项，CSMIS 目前几乎是空白。
4. **日拨付 / 按笔拨付**：即时结算改革的核心创新，当前只有月度拨付。
5. **智能审核申诉/复审/合议闭环**：费用审核目前只有通过/驳回，缺标准闭环。

### 次优先（增强型）
6. 信用管理（记分/评价/联合奖惩）　✅ 已完成
7. 举报投诉 + 奖励　✅ 已完成
8. DRG/DIP 支付监管、药品追溯码　✅ 已完成
9. 双随机一公开、专项整治、自查自纠　✅ 已完成（专项整治含在飞检任务内）
10. 结算清单质控、统计报表深化、个人账户管理、门诊慢特病认定　✅ 全部已完成

### 可选（渠道/行政边界）
11. 网办/掌办/短信渠道、行刑衔接行政端、场景监控（视频/生物特征）、进销存、信息披露/社会监督员/曝光。

## 六、结论

CSMIS 已经把**"即时结算经办 + 基金监管（经办端）"两条主干链路**做得相当完整，尤其经办侧的"报盘→结算→对账→申报→审核→拨付→清算→质保金"闭环和监管侧的"规则→疑点→飞检→追回"闭环是真实可用、有库有数据的。

主要短板集中在两块：

### 7.4 关键实现说明

- **事前提醒/事中拦截**：规则按 `mss_precheck_rule.category` 分派，阈值走 `params`（JSON）。事前只提醒不阻断（阻断级命中在结算页强提示）；事中按 `blockFlag` 与 `riskLevel` 分三档——**阻断→拒付**（不生成结算单）、**高风险→转人工**（生成结算单但置「待审核」并落 `mss_fee_audit` 待办）、其余放行并留痕。
- **大数据反欺诈**：模型按 `mss_fraud_model.category` 分派，数据源为经办结算单（`mss_bill` + `mss_fee_item`）与机构报盘（`mss_settlement`）；按「模型 + 业务单号 + 线索详情」幂等去重。
- **DRG/DIP**：病例按实际费用与组均次费用最近匹配入组；DRG 支付标准 = 权重 × 费率，DIP = 分值 × 分值成本；偏差率 > 20% 预警、> 50% 判定超支，支持特例单议。
- **双随机**：从**已签订协议的定点机构**中无放回随机抽 N 个、从**在职人员**中随机抽 M 名，抽取名单与时间全部留痕，结果可逐条或整体「一公开」。
- **个人账户**：账户余额以 `mss_insured_person.account_balance` 为准，`mss_account_txn` 为流水账；一次性支取校验「已停保 + 必填事由 + 金额不超余额」；完成转移接续时自动结转个人账户（转出方清零并生成转移流水）。
- **慢特病认定**：同参保人同病种不允许重复申请；认定通过自动核定 1 年待遇有效期。
- **结算清单质控**：规则按 `mss_quality_rule.rule_type` 分派 10 类校验（必填项缺失/目录未对照/超限价/数量异常/支付类别缺失/重复上报/金额勾稽不一致/目录已停用/乙类自付比例缺失/性别限制）；每条规则带严重程度与扣款方式（按比例/固定金额），质控命中自动算「建议扣款」；处理环节选择「已确认」时联动生成违规追回扣款单（`sourceType=4`）。
- **药品追溯码**：台账登记（单条/批量扫码采集）→ 结算核验（按结算单对药品类明细逐条匹配，核验通过即核销并绑定结算单与明细）→ 核验日志留痕；六类核验结果：核验通过/码不存在/重复使用/与结算项目不符/已过期/已作废。结算单管理页提供「追溯码核验」入口。
- **基金运行分析**：口径——基金统筹收入 = 统筹支付 + 个人账户支付；基金支出 = 月度结算已拨付合计；基金率 = 支出/收入。输出总览指标卡（总费用/收支/结余/基金率/次均/人均）、险种结构、就诊类型构成、支付类别构成（甲乙丙）、项目类别构成、**定点机构结算排名（并入违规追回扣减金额与笔数）**、日趋势（费用/统筹/个账/现金/**日拨付**）、月度拨付分析（申报/扣减/拨付/扣减率）。
- **监管成效分析**：把审核、疑点、反欺诈线索、事前事中、清单质控、追溯码、违规追回、自查自纠八个环节的总量与待办量汇总到一处，输出审核通过率、疑点确认率、追回金额、自查办结率等指标；这是「监管做了多少、发现多少、收回多少」的总账。
- **药品耗材进销存**：成本采用**移动加权平均法**（入库后重算均价，出库按当前均价结转成本）。与结算链路双向闭环——
  ① **结算出库**：结算确认后自动按药品/耗材类明细扣减库存并生成出库流水（匹配规则：品项名称+规格 → 退化为医保编码）；
  ② **退费红冲**：退费时自动生成反向入库流水回补库存。
  库存不足时**不阻断结算**（临床已实际用药），而是形成负库存并在流水标记异常，交由盘点核查——这正是账实不符的信号。
  提供库存预警（低于下限）、负库存预警、盘点账实相符率、分类库存金额分析。

### 7.9 第八批：菜单三级化重构

原菜单顶级混着目录与页面——「工作台」「医保目录管理」「清算对账」「定点协议管理」等 8 个页面直接挂在
`parent_id=0`，而「基金监管」一个目录下塞了 15 个子菜单。用户分不清哪个菜单归哪块，
平台将来拆分（经办端独立部署 / 监管端独立部署）也没有干净的边界。

**重构后的结构（顶级只有三个业务域）**

| 顶级 | id | 二级分组（业务分组） | 三级页面数 |
|------|-----|---------------------|-----------|
| **医保结算经办** | 2 | 结算经办 / 结算与清算 / 参保与账户 / 费用与目录 / 待遇与备案 / 进销存 / 经办看板 | 20 |
| **医保基金监管** | 13 | 监管总览 / 规则与知识 / 稽核核查 / 智能监管 / 专项监管 / 信用管理 | 15 |
| **系统管理** | 9 | 用户与权限 / 组织与岗位 / 基础配置 / 审计与待办 | 9 |

合计 **3 顶级 + 17 二级分组 + 44 三级页面 + 12 按钮 = 76 条菜单**。

**技术实现**

| 层 | 改动 |
|---|---|
| 前端 | 新增 `components/MenuTreeNode.vue` —— **递归菜单组件**（原先 `MainLayout.vue` 只渲染两层，三级渲染不出来）；折叠态降级为平铺；面包屑改为按当前路径在菜单树回溯，输出「域 › 分组 › 页面」；新增三级视觉层次样式（顶级加粗最亮 → 二级中等 → 三级最淡） |
| 后端 | `AuthServiceImpl.buildTree` 原本就是递归的，无需改动；`SystemMenuServiceImpl.deleteById` 的 `collectTreeIds` 也是递归的，三级删除天然支持 |
| 数据 | `data.sql` 菜单段整体重写为三级结构（含显式 id，关联表主键无自增）；`SchemaPatchInitializer` 新增 `migrateMenuTree()` —— 存量库启动自动升级，幂等（两次启动均为「新建 0 / 补授权 0」） |
| 约束 | 三级页面的 `path` 必须与 `front_mis` 路由一一对应（联调脚本逐条核对 44 个页面）；页面的 `parent_id` 变更后，角色授权要补上新的祖先链（顶级域 + 二级分组），否则菜单树挂不上、页面点不到 |

**角色可见范围**

| 角色 | 顶级 | 二级分组 | 页面 |
|------|------|---------|------|
| 经办管理员（1） | 三域全量 | 17 | 44 |
| 经办员（2） | 医保结算经办 | 7 | 21 |
| 审核稽核员（3） | 医保基金监管 + 医保结算经办（仅审核相关） | 6 + 2 | 15 |

**踩过的坑**

- 二级分组的 `menu_key` 一开始取 `settle.catalog` / `system.user` 等，与三级页面撞车 ——
  `sys_menu` 上有 `UNIQUE KEY uk_menu_key`，`ON DUPLICATE KEY UPDATE` 静默生效，
  **5 个分组凭空消失**（语句报 ok 但数据没进去）。改为统一加 `group.` 前缀。
- 重写 `data.sql` 菜单段时用正则逐段替换，替换后的文本又命中了模式，导致旧段残留、菜单数翻倍
  （304 条 vs 应有 76 条）。改为「先一次性删除全部旧段，再插入新段」。
- `sys_role_menu.id` 无 `AUTO_INCREMENT`（主键由 entity 生成，此处是纯 SQL 种子），
  不显式给 id 会因主键冲突被 `INSERT IGNORE` **静默跳过** —— 角色菜单数据全丢。

**验证**：Playwright 实际截图确认 20 个折叠组 + 44 个页面全部渲染、零控制台错误；
端到端脚本新增 13 项菜单断言（顶级三域、二级 17 组、三级 44 页、无空分组、
44 个页面路由全部命中、三个角色的可见范围），**总计 56 项断言全部通过**。
